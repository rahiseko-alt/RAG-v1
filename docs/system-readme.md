# medguide-rag System README

この文書は、medguide-rag が「何をする仕組みなのか」「なぜその構造が必要なのか」「どこを直せば品質が上がるのか」を説明するためのREADMEです。

## 1. ひと言でいうと

medguide-rag は、登録済みナレッジに基づいて回答するRAGに、回答検品、出荷停止、ナレッジ版管理、before/after比較、回帰検査、監査記録、弱点発見ループを組み合わせた品質改善ワークベンチです。

目的は、LLMにただ答えさせることではありません。

目的は、次の流れを運用できるようにすることです。

```text
質問する
-> 根拠を検索する
-> 回答候補を作る
-> 根拠に支えられているか検査する
-> 危ない回答は止める
-> どこが悪かったか分類する
-> ナレッジや検索設定を調整する
-> before/afterで改善を確認する
-> 回帰悪化がなければ有効化する
```

## 2. 解決したい問題

通常のRAGは、質問に対してそれらしい回答を返せても、次の問題が残ります。

| 問題 | 何が困るか |
|---|---|
| 根拠なし回答 | ナレッジにないことを自然に言ってしまう |
| 検索失敗 | ナレッジにあるのに必要なチャンクが取れない |
| 生成失敗 | 根拠は取れているのに回答に反映できない |
| 判定不能 | 類似度やスコアだけでは正しいか判断できない |
| 修正不能 | どこを直せばよいか非エンジニアには分からない |
| 改善未確認 | ナレッジを足しても本当に良くなったか分からない |
| 副作用 | ある質問は改善したが、既存の正答が壊れる |
| ブラックボックス | 処理工程で何が起きたか見えない |

この製品は、これらを「回答する前後の品質管理工程」として扱います。

## 3. 基本構成

| 層 | 役割 | 主な実装 |
|---|---|---|
| ナレッジ層 | Markdown/Text/PDFなどの登録済み文書を管理する | `config/knowledge.toml`, revision source files |
| 検索層 | 質問に近い根拠チャンクを取得する | Chroma, BM25 rescue, neighbor expansion, rerank |
| 構造化ナレッジ層 | entity/fact形式で関係情報を補助検索する | `src/structured_knowledge.py`, `src/structured_extraction.py` |
| 回答生成層 | 取得根拠だけを材料に回答候補を作る | `src/rag/__init__.py` |
| 回答照合層 | 回答の主張が根拠に支えられているか検査する | `src/quality/verifier.py` |
| 出荷ゲート | NG、判断不能、検査エラーを表示前に止める | `QualityWorkbench.answer_question()` |
| 版管理層 | ナレッジrevision、承認、却下、有効版を管理する | `src/quality/store.py` |
| 比較・回帰層 | before/afterと既存質問の悪化を検査する | comparison / validation jobs |
| 監査層 | run ID、trace ID、Langfuse状態を記録する | `src/observability.py`, SQLite |
| 弱点発見層 | A/B/C/Dループで問い型ごとの弱点候補を出す | `src/coverage_loop.py` |
| UI層 | 非エンジニアが工程・根拠・結果を確認する | FastAPI static UI |

## 4. 回答処理の考え方

回答処理は「答える工程」ではなく「出荷判定付きの製造工程」として設計しています。

### 4.1 質問受付

ユーザーの質問を受け取り、対象ナレッジrevision、回答モード、run ID、trace IDを決めます。

ここで重要なのは、同じ質問でも、どのrevision・どの設定で処理したかを後で追えることです。

### 4.2 検索

検索は単純なベクトル検索だけにしません。

| 検索手段 | 目的 |
|---|---|
| ベクトル検索 | 意味が近いチャンクを取る |
| BM25 rescue | 固有名詞や表記一致を拾う |
| neighbor expansion | 前後チャンクにある説明を拾う |
| rerank | 質問語との対応が強い根拠を上位にする |
| structured hits | entity/fact化した関係情報を補助する |

この設計にした理由は、マニアックな質問や因果質問では、単語の近さだけでは根拠が足りないからです。

### 4.3 回答生成

LLMはシェフのような役割です。

Chromaや構造化ナレッジが材料を渡し、プロンプトが調理ルールを決めます。

ただし、シェフが勝手に外の情報を買いに行くことは許しません。回答は取得された根拠だけに縛ります。

### 4.4 回答照合

回答候補はそのまま表示しません。

まず機械検査をします。

- 引用番号が実在するか
- 事実主張に引用があるか
- 根拠0件なのに断定していないか
- 文書外質問に「記載なし」と答えているか
- 空回答、途中切れ、形式破損がないか

次に別LLM照合で、回答を主張単位に分けます。

| 判定 | 意味 |
|---|---|
| 支持あり | 根拠チャンクが主張を支えている |
| 矛盾 | 根拠と回答が食い違う |
| 判断不能 | 根拠が足りない |

矛盾、判断不能、検査エラー、timeout、JSON破損は出荷停止です。

### 4.5 出荷ゲート

PASSだけ回答欄に表示します。

NGの場合、候補回答は表示しません。表示するのは停止理由と、どの工程で止まったかです。

これは「危ない回答を出さない」ためのfail-closed設計です。

## 5. ナレッジ調整の考え方

この製品の肝は、回答結果を修正することではありません。

肝は、**なぜ悪かったのかを分類し、調整し、改善したか記録すること**です。

代表的な原因分類は以下です。

| 原因 | 意味 | 修正対象 |
|---|---|---|
| `missing_knowledge` | ナレッジに必要情報がない | ナレッジ追加 |
| `retrieval_failure` | ナレッジにはあるが検索できない | 検索・chunk・metadata |
| `generation_failure` | 根拠はあるが回答化できない | プロンプト・回答モード |
| `chunking_failure` | 根拠が分割で壊れている | chunk設定・文書構造 |
| `invalid_A` | 外部基準回答が怪しい | 外部基準を却下 |
| `ambiguous_question` | 質問が曖昧すぎる | 評価質問を分解 |
| `out_of_scope` | 対象ナレッジ外 | no-answerセットへ |

この分類をしないと、何でもナレッジ追加で解決しようとして、ナレッジが肥大化します。

## 6. A/B/C/D Coverage Loop

Coverage Loop は、RAGの弱点を見つけるための仕組みです。

これは「ナレッジ不足を確定する装置」ではありません。

正確には、**RAG弱点仮説生成・検証ワークフロー**です。

| 役 | 役割 |
|---|---|
| C | 弱点を突く質問を作る |
| A | 外部基準ではどう答えられるかを作る |
| B | 現行ナレッジだけでどう答えるかを作る |
| D | A/Bを比較し、Bの失敗原因を分類する |

基本条件は次です。

```text
Aが妥当
Bが不十分
Dが原因分類を出す
-> 改善候補
```

ただし、改善候補はすぐ正本化しません。

原因に応じて、自動採用、自動却下、隔離に分けます。

## 7. C役を複数にする理由

質問者が1人だと、質問の癖がそのまま評価の癖になります。

そのため、C役は複数に分けます。

| C役 | 掛け合わせ軸 | 狙い |
|---|---|---|
| C-1 | 因果 x マニアック | 深い設定・裏設定・術式仕様の因果 |
| C-2 | 因果 x 複数人/組織 | 人物・組織・陣営への波及 |
| C-3 | 条件/例外 x 時系列/比較 | 条件、例外、通常との差、時系列変化 |

今後はさらに、実ユーザー質問、曖昧質問、手順系、エラー系、権限系、no-answer系も追加する必要があります。

## 8. 自動運用方針

ユーザーが毎回判断すると、改善が止まります。

そのため、通常候補は自動で処理します。

```text
candidate
-> auto_classified
-> auto_approved / auto_rejected / auto_quarantined
-> implemented
-> verified
-> active
```

| 状態 | 意味 |
|---|---|
| `candidate` | 弱点候補 |
| `auto_classified` | 原因分類済み |
| `auto_approved` | 自動基準を満たし実装対象 |
| `auto_rejected` | 対象外、重複、出典弱いなど |
| `auto_quarantined` | 判断不能。処理は止めず隔離 |
| `implemented` | 修正反映済み |
| `verified` | before/afterと回帰検査PASS |
| `active` | 有効版へ反映 |

ユーザーが見るのは隔離だけです。

## 9. before/after と回帰検査

ナレッジを直したら、同じ条件で比較します。

固定する条件:

- 生成モデル
- 検証モデル
- プロンプト版
- 埋め込みモデル
- top-k
- chunk設定
- 評価セット
- ナレッジrevision

対象質問が改善しても、既存PASS質問がNG化したら承認しません。

## 10. 監査と透明化

処理工程は、非エンジニアにも見える必要があります。

ただし「何をする予定か」では不十分です。

表示すべきなのは、実際に **何をしたか** です。

| 表示 | 内容 |
|---|---|
| 質問受付 | 入力質問、正規化後質問、run ID |
| ナレッジ選択 | revision、source SHA、active状態 |
| 意味検索 | 検索対象チャンク数、取得チャンク、順位、score |
| 根拠候補確認 | 取得根拠の抜粋、source、chunk ID |
| 回答生成 | 使用モデル、回答候補、引用 |
| 回答照合 | 主張別判定、根拠対応 |
| 出荷判定 | released / blocked と理由 |
| 監査記録 | trace ID、Langfuse状態、run保存 |

## 11. この仕組みでカバーできないこと

| 限界 | 内容 |
|---|---|
| Aの誤答 | 外部基準が間違えば誤った改善候補になる |
| Dの偏り | 長いAを好む、順序に影響されるなど |
| 網羅性 | 100問回しても全穴を保証しない |
| 公式性 | 非公式・考察・二次情報の混入は別途管理が必要 |
| 実ユーザーの曖昧文 | C役の作問だけでは再現しにくい |
| 表/画像/PDF固有情報 | テキスト化・構造化が別途必要 |
| 古い情報 | 更新日・版管理をしないと劣化する |

そのため、この製品は「完全自動で正解を作る装置」ではありません。

RAGの弱点を見つけ、原因を分類し、安全に改善を回すためのワークベンチです。

## 12. 次に実装すべきこと

1. D判定スキーマに失敗原因分類を正式追加する。
2. A回答に source URL、source type、根拠span、更新日、confidence を必須化する。
3. B回答に retrieved chunks、score、引用箇所、検索順位を必須化する。
4. coverage台帳をSQLiteに保存する。
5. 自動採用、自動却下、隔離の状態遷移を実装する。
6. 隔離一覧API/UIを追加する。
7. 30問セットをA/B/Dへ流し、問い型別の弱点分類表を作る。
