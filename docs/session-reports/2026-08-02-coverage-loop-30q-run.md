## 結論（先に読む所）

**30問は全問流し切った。だが「問い型別の弱点分類表」は作れなかった。** 30問中 **24問が `needs_quarantine`**（分類不能）に落ちたためである。これは実装のバグではなく、**設計どおりの fail-closed 動作**であり、そのこと自体が項目6の答えになっている。

> **今のループ構成では、`missing_knowledge` / `retrieval_failure` / `chunking_failure` を分離できない。** D にコーパス側の情報が一切渡らないため、「引けたチャンクに答えが無い」という観測は3原因のどれとも等しく整合し、D は正しく判断を放棄する。

したがって次の一手は「30問を増やす」ことでも「D のプロンプトを直す」ことでもなく、**D に『コーパスにその事実が無い』と言える証跡を与える経路を作ること**である（後述「次にやるべきこと」1）。

## APIキー無しで、どこまで本物を回したか

キー未設定のため、**B の生成・D の判定・A の回答をサブエージェントが代役**した。ただし「代役した所」と「本物が動いた所」は厳密に分けてある。

| 工程 | 実行主体 | 本物か |
|---|---|---|
| C（設問生成） | 前セッションで生成済み・版管理下 | 固定入力（今回生成していない） |
| **B の検索** | **製品コード（e5 + Chroma + BM25 rescue + neighbor + rerank）** | **本物**。`scripts/coverage_loop_retrieve.py` が `retrieve` ノードと同一段を実走 |
| B の生成 | サブエージェント | 代役。本番と同一の `SYSTEM_PROMPT` と同一の抜粋を入力 |
| A（外部基準回答） | サブエージェント（WebSearch / WebFetch） | 代役。出典URLは実際に取得したものだけ |
| D（判定） | サブエージェント | 代役。`LLMFactChecker` のプロンプト内容を踏襲 |
| **候補化・台帳化** | **製品コード（`run_revision_coverage_loop` の注入経路）** | **本物**。`allow_llm_agents=false` / `run_knowledge_answerer=false` |

**偽造しなかったもの（重要）**：

- **B の `retrieved_chunks` / `sources` は合成していない。** 実走した検索の出力そのものである。注入B回答に証跡を合成すると D の前に偽の evidence を置くことになり、taxonomy が成立しなくなる（`memory.md` [importance:H] 2026-08-02）。
- **B の `status` は `released` ではなく `ok`。** オンライン品質ゲートの意味論的判定は LLM verifier を要し、今回は動いていない。**動かなかった判定を下ったことにしない。** ゲートの決定論的な半分だけはキー無しで動くので実行し、**観測値として別枠に記録**した（リリース判定としては使っていない）。
- 代役である旨は各B回答の `notes` に文字列として残るので、台帳の読み手が本番実行と取り違えることはない。

## 判明した問題（次に効く順）

### 1. D がコーパスを見られないため、24/30 が分類不能になる

これは設計上の意図（`RetrievedChunk` の docstring・`memory.md` [importance:H]）どおりの挙動だが、**その結果ループの出力が「隔離の山」になり、ユーザーが確認すべき隔離だけを見る運用が破綻する**（24件は「まとめて確認」できる量ではない）。原因分類を導入した以上、D に**コーパス側の不在証跡**を渡す経路が要る。

### 2. D が見ているのは各チャンク先頭240字のスニペットだけ

`generation_failure` は「引けたチャンクに事実がある」ことの確認を要するが、D に渡る `sources[*].snippet` は先頭240字に切られている。判定を担当したサブエージェントの1体が明示的に指摘している——**B が回答本文で引用している記述がスニペットに現れておらず、チャンク本体の未可視部分に事実があることが確定していた**（C2グループ）。つまり **240字より後ろにある事実は `generation_failure` として拾えず、自動的に隔離へ落ちる**。今回 `generation_failure` が2件しか出なかったのは、この打ち切りによる過小評価である可能性が高い。

判定用の入力に限っては、`_evidence` が既に持っている private 側の全文（`text`）を D に渡すべきである（公開APIの応答に足すという意味ではない）。

### 3. B の誠実な部分回答が、決定論ゲートを25/30で落とす

B の30問すべてが「抜粋から言える所は答え、言えない所は『提供された抜粋からは特定できません』と明記する」型になった。この最後の一文には引用番号が付かないため、決定論チェックの **`citation_coverage` が 25/30 で fail** する（落ちた検査は全件これ1種類）。

- 完全な抽象（`提供された文書には記載がありません` の一文のみ）は `_is_canonical_abstention` で免除されるが、**部分回答＋部分留保は免除経路が無い**。
- 本番では、この型の回答は品質ゲートで**ブロックされる**。つまり「正直に留保する良い回答ほど出荷されない」構造になっている。
- どちらを直すかは設計判断が要る（留保文を免除対象にする／B に留保文へも引用を付けさせる／部分留保を別ステータスにする）。**今回は観測に留め、変更していない。**

### 4. A の出典が公式ゼロ

30問すべてで `official` / `primary` の出典が**1件も取れなかった**。内訳は fan のみ17問、fan＋reliable_secondary 11問、reliable_secondary のみ2問。`jujutsu-kaisen.fandom.com` は 402/403、TVアニメ公式 `jujutsukaisen.jp` も 403 で本文取得できなかったことが理由として報告されている。

設計レポートの自動採用条件は「A の `source_type` が `official / primary / reliable_secondary`」であり、**このドメインでは A の出典品質が律速になる**。なお D が `invalid_A` を出したのは1件だけで、`external_status` は 23/30 が `pass` だった。**D の A 評価は、自動採用条件より緩い。** 昇格ロジックを書く際に、D の `pass` をそのまま採用条件に流用すると、fan 単独出典が採用される。

### 5. 小コーパスでは `retrieval_failure` がほぼ主張できない

41チャンク中24チャンク（58%）が毎回 surface する。この網羅率では「あるのに引けなかった」と言える余地が小さく、原因分布が隔離側に寄る一因になっている。**この観測は今回のコーパス規模に固有**であり、大きなコーパスへ一般化してはいけない。

### 6. D の誤検知が1件（記録のみ・実害なし）

複数の D 担当が「`rank` の順序と `score` の順序が一致しておらず、検索が壊れている疑い」と報告した。**これは仕様どおりで欠陥ではない。** `rerank_retrieved_documents` が語彙リランクスコアで並べ替えて `rank` を振る一方、`score` はベクトル類似度をそのまま保持するため、両者の順序は一致しない。D にはリランクの存在が見えないため生じた誤読である。判定の分類には使われていないため実害は無いが、**D へ渡す情報に `rerank_score` を含めるか、リランクの存在を明示すべき**である。

## 次にやるべきこと

1. **D にコーパス不在証跡を渡す経路を作る**（問題1）。案：判定前に、A の回答から抽出したキーワードでコーパス全体（検索ではなく全走査）を引き、`missing_knowledge` を主張できるだけの「不在の証拠」を作って D に添える。これが入って初めて、隔離24件が意味のある分類に割れる。
2. **D の判定入力を private evidence の全文にする**（問題2）。240字打ち切りのままでは `generation_failure` が構造的に過小評価される。ここは小さい変更で効果が大きい。
3. **部分回答＋部分留保に対する品質ゲートの扱いを決める**（問題3）。設計判断であり、実装より先に方針を決める必要がある。
4. **`auto_classified -> auto_approved` の自動昇格**は、上記1〜2が入って隔離が割れてからでよい。今の入力（`add_candidate` 2件）では before/after 比較の母数が小さすぎる。加えて、昇格条件の A 出典要件を **D の `external_status` とは別に**評価すること（問題4）。
5. **quarantine 一覧 UI**（`src/api/static/app.js`）の優先度が上がった。24件が隔離に積まれた以上、画面が無いと運用できない。

## 根因と修正

根因は2つで、どちらも**プローブの精度ではなく、証拠の扱い方の設計**にある。

1. **語一致は言い換えを検出できない**のに、D への指示でその不在を「強い証拠」と呼んだ。
2. **D は各チャンク先頭240字のスニペットしか見られない**ため、**強い証拠（取得済みチャンクの本文）を
   確認する手段を持たないまま、弱い証拠だけを増やした。**

修正（実装済み）：

- **`AgentAnswer.surfaced_texts` を追加**し、**B に渡された全チャンクの全文**を D に渡す。
  判定専用の経路であり、**台帳にも API 応答にも載せない**（`run_revision_coverage_loop` で判定後に除去）。
  コーパスの二重保持を避けるため。
- **D の判定手順を順序付きで固定**した。手順1で `surfaced_texts` を読み、**言い回しが違っていても
  質問に答えているチャンクがあれば `generation_failure` で確定**。手順2はそれを排除できた時だけ
  プローブを使う。手順3はどちらでも決まらなければ隔離。
- プローブの `method` 文言と docstring に、**「言い換えを検出できない」ことと実測の誤り率**を明記した。
