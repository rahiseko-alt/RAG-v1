# Phase 4（ドメイン移植性）着手と、他セッションの作業を消した事故

2026-08-04。Phase 3 完了・公開ポートフォリオ化・手順0完了に続けて、Phase 4 の
ドメイン移植性に着手した記録。**作業中に他セッションの成果を force-push で消す事故を起こした**ため、
その顛末も併せて残す。

## 4-1 ドメイン語彙を設定へ外出し（PR #33・`fce4bfe`）

### 問題

`src/rag/__init__.py` が既定コーパスの語を直接持っていた。

- `_query_terms` の除外語に作品名
- `_intent_terms` に `術式` / `領域` / `声優` / `作者`
- `_lexical_rerank_score` に術式マーカー一式

このため `config/knowledge.toml` を別ドメインへ差し替えても検索は旧ドメイン向けに
チューニングされたままで、`src/coverage_loop.py` のコーパスプローブも `_query_terms` 経由で
同じ語を継承していた。README の「差し替えのみで切り替えられます（コード変更は不要です）」という
記述は、この点で正確ではなかった。

### 解決

`config/knowledge.toml` に `[lexical]` 節を新設し、`stop_terms` / `generic_terms` /
`[[lexical.intents]]`（`triggers` / `markers` / `paired_markers` / `proximity_terms` /
`demoted_terms`）を宣言する形にした。エンジンは意図を特別扱いせず、宣言された全意図へ
同じ規則を適用する。

日本語の文法語と疑問詞は `LANGUAGE_STOP_TERMS` / `LANGUAGE_GENERIC_TERMS` としてコードに残し、
設定値と**マージ**する（置換しない）。`[lexical]` を書かない設定でも日本語のトークン化が
壊れないようにするため。

**受入条件 `grep -r "呪術廻戦" src/` は 0件。**

## 4-2 表記ゆれ正規化（PR #34・`d958bcd`）

### 問題

正規化は繰り返し記号（`日々`）の展開だけだった。`5mg` と `5 mg`、`COVID-19` と `ＣＯＶＩＤ-19` が
別の語として扱われ、**質問と文書で書き方が違うだけで一致に失敗する。しかもエラーにならず
無言で見つからない。** 医療コーパスでは用量表記がまさにこの形を取る。

### 解決

NFKC・casefold・数値と単位の間の空白詰めを追加した。いずれも表記のレベルの話でコーパス固有の
語彙ではないため、`[lexical]` には出さずコードに置く（`LANGUAGE_STOP_TERMS` と同じ線引き）。

空白を詰めるのは**欧字の前だけ**。`5 日` を `5日` にすると数量と助数詞の境界が失われる。

正規化は `src/text_normalize.py` へ切り出した。`src/rag` と `src/structured_knowledge` の双方が
必要とし、後者に langchain / torch を引き込むわけにいかないため。繰り返し記号の展開は**元々2ファイルに
同じ実装が重複**しており、これも解消した。構造化ナレッジ検索も同じ幅・単位の扱いを得ている
（従来は casefold のみの狭い正規化だった）。

## 事故：他セッションの作業を force-push で消した

### 何が起きたか

同じ作業ブランチ `claude/checkin-8obqof` を別セッションが使っており、そちらが 4-1 の実装
（`fa7e1de`）と設定変更（`1e2025f`）をコミットし、**PR #33 も立てていた**。こちらはそれを知らずに
同じ 4-1 を実装し、`--force-with-lease` 付きで push した結果、リモートの2コミットを上書きして消した。

PR の説明文だけが別実装（`demoted_terms` / `test_lexical_profile.py` / mtime キャッシュ）を
指したまま残り、ブランチ上のコード（`penalty_terms` / 別ファイルのテスト / キャッシュなし）と
食い違って初めて気づいた。

### なぜ `--force-with-lease` が効かなかったか

この機能は「自分の remote-tracking ref と実際のリモートが一致するか」で判定する。
その直前に

```bash
git checkout -B claude/checkin-8obqof origin/main
```

を実行しており、**この操作でローカルの参照を作り直したためリースの基準が古くなり、
安全装置が素通りした**。「マージ済み PR の後はブランチを main から作り直す」という運用ルール
自体は正しいが、同じブランチ名を複数セッションが使う前提が抜けていた。

### 復旧と判断

`fa7e1de` / `1e2025f` は reflog に残っており復旧できた。両実装を**コードで**比較した結果、
別セッションの実装が全ての観点で上回っていた。

| 観点 | 別セッション | こちら |
|---|---|---|
| プロファイルを質問ごとに1回取得して下位へ渡す | ✅ | ✅ |
| `(path, mtime)` キャッシュ | ✅ | ❌ |
| 不正な設定 | **例外にする**（存在しない場合だけ言語既定へ） | ❌ 全例外を握り潰す |
| 既存テストの非判別性 | **発見して修正** | ❌ 見落とし |
| ソースにドメイン語が無いことの直接検査 | ✅ | ❌ |

移植すべき点が無かったため、こちらの実装は破棄して別セッションのものを採用した。

**PR 説明文だけを見て判断していたら誤っていた。**「相手の方がキャッシュしている＝こちらは
質問ごとに1回読む方式で優位」と考えていたが、コードを読むと相手も同じ方式を採ったうえで
さらにキャッシュしていた。

## 同じ型の失敗を4回繰り返した

「テストが緑」と「テストが主張どおりの経路を通っている」は別、という失敗を 2026-08-03 に
記録したにもかかわらず、この日だけで3回繰り返した。

1. Phase 4-1 の初版テスト — bm25 と実体一致の加点だけで順位が決まり、意図設定が効かなくても通った
2. Phase 4-2 のテスト — **テスト内で文書側を自分で正規化してから**突き合わせており、
   エンジンの文書側正規化を外しても通った（CodeRabbit の指摘で発覚）

**2件に共通するのは「テスト側で前処理をしてから比較した」こと。** 前処理をテストが肩代わりすると、
その前処理を担うはずの本体コードが検証対象から外れる。**入力は生のまま渡し、本体に処理させる。**

対策として、新しいテストを書いた直後に**対象コードへ回帰を注入し、期待どおり失敗することを
見てから復元する**手順を踏むようにした。今回は `assert 5.0 > 9.5` という失敗を確認できている。

## 次にやるべきこと

Phase 4 の残りは **pip-audit と CodeQL を `ci-green` に接続すること**のみ。
`AGENTS.md` が「既知の欠落」と明記している唯一の項目が pip-audit である。

⚠ 上流ジョブを増やす場合は `needs:` とゲート内の比較式の**両方**を必ず同時に直す
（片方だけだと workflow が startup failure になり `ci-green` の check run が生成されず、
branch protection が永久に待ち状態になる）。コミット衛生ガードは、この危険を避けるため
新規ジョブではなく `quality` ジョブのステップとして追加してある。同じやり方が安全。
