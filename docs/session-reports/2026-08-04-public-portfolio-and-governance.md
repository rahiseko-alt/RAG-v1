# 公開ポートフォリオ化と統治の完了（2026-08-04）

Phase 3 完了後、ユーザーから「このリポジトリをポートフォリオとして公開して問題ないか」という
問いを受けて調査し、見つかった問題を修正した記録。あわせて `AGENTS.md` に「未実施」と
書かれ続けていた**手順0（機械強制の有効化）が完了**した。

## 調査で分かったこと

リポジトリは既に Public（2026-08-01 から）だったため、「公開してよいか」ではなく
「公開されている現状に問題がないか」が実際の問いだった。

### 致命的な問題は無かった

- 秘密情報：APIキー・トークン・秘密鍵は**作業ツリーにも全履歴にも存在しない**。
  `.env` は一度もコミットされていない。
- 法的リスク：低い。呪術廻戦ナレッジは台詞・本文の転載ではなく要約で、出典とライセンスを
  データカードに明記済み。WHO の PDF は CC BY-NC-SA 3.0 IGO で、非営利の個人ポートフォリオと
  いう現在の用途は条件に適合する（**商用に転じる場合は条件違反になる**点は要注意）。

### メール流出の原因は想定と違った

個人メールを含むコミット28件を調べたところ、**全てが GitHub の生成したマージコミット**
（`Merge pull request #NN from ...`）だった。これは GitHub がマージ時にアカウントの公開メール
設定で刻むもので、**どのPCの `git config` を変えても防げない**。

## 実施したこと

### 1. メール流出の停止（アカウント設定＋機械ガード）

- **アカウント設定**（人の操作が必要・AIには実行できない）：GitHub → Settings → Emails →
  「Keep my email addresses private」と「Block command line pushes that expose my email」を ON。
- **CI に機械ガードを追加**：PR の差分コミットの author/committer が noreply でなければ赤にする
  （`.github/workflows/ci.yml` の「コミット衛生」ステップ）。ローカル設定の漏れをこれで止める。
  検査対象を PR 差分に限定したのは、既存履歴に過去のマージコミット由来の個人メールが残っており、
  全履歴を対象にすると恒久的に赤になるため。`ci-green` の契約（job 名・`needs`・比較式）は
  一切触っていない。

**効果の実測**（自己申告ではなく実コミット）：

|---|---|
| `caa2545`（設定ON前） | `rahiseko@gmail.com` |
| `ef97e48`（設定ON後） | `228135523+rahiseko-alt@users.noreply.github.com` |

以降のマージ8件も全て noreply。

## 今回持ち込んだ不具合（自分で発見・修正）

**コミット衛生ガードが Dependabot PR を全て赤にしていた。** 許可パターンのローカル部を
`[A-Za-z0-9._-]` としたが、bot のアドレスは `49699333+dependabot[bot]@users.noreply.github.com`
の形を取り、**角括弧がクラスに含まれていなかった**。Dependabot PR に触る直前に、実際の author
メールを確認して発覚（PR #30 で修正）。失敗ジョブが8秒で終わっていたことが、重い install の前に
置いた早期ステップでの即死＝この不具合であることの裏付けになった。

**教訓**：許可リスト（allowlist）を書くときは、**実際に通したい対象の実データを取得して
突き合わせる**。想定した文字種だけでクラスを組むと、bot アカウントのような「人間とは違う形」を
落とす。今回は修正前に、実在の Dependabot ブランチの `%ae` を読んで確認した。

## 意図的に実施しなかったこと

**Git 履歴の書き換え。** 個人メール28件、旧 `memory.md` の内輪の記述、削除した私的メモは
`git log -p` で今も読める。消すには履歴書き換えが必要だが、

- ハンドル `rahiseko-alt` とメール `rahiseko@gmail.com` は文字列が同じで、隠しても推測できる
- 公開から3日経っており、過去の露出は取り消せない
- PR のレビュー履歴（敵対検証で実バグを見つけた記録＝このポートフォリオの一番の差別化要素）を
  痛める

以上から、現状維持が妥当と判断した。**この判断はユーザーに提示済みで、実施を希望する場合は
`git filter-repo` で新規リポジトリではなく同一リポジトリを書き換える**（新規リポジトリだと
PR のレビュー履歴が置き去りになるため）。
