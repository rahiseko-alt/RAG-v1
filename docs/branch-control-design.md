# 分岐制御 仕組み — 設計（検証済み・信頼性を機械強制するルーティング機構）

> 本書は**提案**。vibe-base 本体（hooks/skills/settings）への配備は担当AIは行わない（マスター判断）。
> medguide-rag の ML/RAG 各 Stage は、この分岐条件を導出・検証するための**実例（実験台）**だった。本質は医療ではなく**分岐制御**。
> 初版は敵対的サブAI検証で **VERDICT=未達成**（核が空論）と判定され、本版はその指摘を潰した再設計。

## 0. 本質（1行）
成果物・操作の性質を**条件判定**し、合致した**強制手順**を**機械ゲート**で発火させ、AIの裁量で飛ばせなくする一般制御。

## 1. 検証で確定した設計原則（初版の失敗から）
初版を general-purpose サブAIに敵対検証させ、以下が確定した。これが本設計の土台。

| 原則 | 根拠（初版で壊れた点） |
|---|---|
| 機械強制が効くのは**帯域外チョークポイントを持つ枝だけ** | git hook / Write hook / permission を通らない枝（チャット直答）はブロック不能 |
| **形式検査は真偽と直交**（意味を担保しない） | 「定説見出しの存在」「http URLが1つ」等は、空の見出し・無関係URL・自作ブロックで全通過 |
| サブAI検証は**主AIが触れない別プロセスで署名付き実行**が必須 | 主AIが「サブAI検証済」ブロックを自作でき、無限後退が切れない |
| **正直なスコープ**が信頼の前提 | 強制できない枝を"飛ばせない"と名乗ると空論になる |

## 2. 三要素
| 要素 | 役割 |
|---|---|
| 分岐条件 | 成果物/操作を分類するルール（**機械評価可能に設計するのが必須**） |
| 強制手順 | 条件に紐づく必須手続き（例: 3層防御・スクショ・レビュー） |
| 機械ゲート | 手順の完了を**署名検証**し、未了なら Write/commit をブロック（exit≠0・deny-by-default） |

## 3. 条件を「機械判定可能」に落とす二層
| 種別 | 判定 | 強制力 | 例 |
|---|---|---|---|
| 直接検知型 | hook が diff パス/内容/コマンドを正規化後に機械検知 | **本物の強制**（チョークポイント有） | UI（出力に`<html`）・コード（`*.py`差分）・破壊操作（`rm`正規化後） |
| 型宣言型 | 成果物 frontmatter の種別＋必須要素を機械検査 | ファイル成果物に限り強制可 | 信頼物（`deliverable: report/analysis/rag-answer`） |

> 初版は型宣言型に「チャット直答」まで含めて空論化した。**本版は型宣言型を"ファイル成果物"に限定**（下記スコープ）。

## 4. 分岐条件テーブル
| # | 分岐条件 | 強制手順 | 機械ゲート | 強制可否 |
|---|---|---|---|---|
| 1 | 信頼物のファイル納品（`deliverable:` 宣言） | **3層防御**（§5） | 独立verifierの署名を検証／未署名・型未宣言はブロック | **可**（Write/commit hook） |
| 2 | UI/デザイン成果物（出力に`<html`/`<!doctype`） | full-page+モバイル スクショ保存 | スクショ実ファイルの存在・生成時刻 | 可 |
| 3 | 破壊的操作（`rm`/`push --force`等・**正規化後**判定） | 停止→確認 | pre-bash hook が deny/ask | 可 |
| 4 | コード変更（`*.py`/`*.ts`差分） | レビュー発火＋検証EXIT0 | commit前hookでレビュー記録＋test結果 | 可 |
| 5 | 外部送信/公開/納品 | マスター承認ゲート | 送信前hookが承認記録を要求 | 可 |
| — | **チャット直答の信頼主張** | 規律＋抜き取り監査 | **機械強制不能**（output hook不在） | **不可・正直に明記** |

## 5. 分岐#1「3層防御」完全仕様（署名ベース・偽装耐性）
発火条件: `deliverable:` 宣言のあるファイルの Write/commit。**未宣言ファイルは deny-by-default でブロック**（入口を塞ぐ）。

| 防御 | 手順 | 合格基準（意味検査・偽装耐性） |
|---|---|---|
| ① 根拠定説 | 争いのない権威レベルの定説を明示 | 別AIが「本文の主張を定説が支持するか」を判定した**署名付き結果**が支持 |
| ② 一次URL | 定説の一次情報URL | verifier が URL を**実fetch**し、到達性＋主張キーワードの本文含有を確認 |
| ③ サブAI check | 独立 runner が整合/不一致を判定 | 検証は**主AIが触れない別プロセス**が成果物ハッシュに対し実行し、署名付きログを外部出力。ゲートは**署名を検証**（ブロックの存在検査ではない） |

不合格時: 成果物を「未検証」とし Write/commit をブロック。ガード必須: 相関≠因果／医療助言でない旨／断定は裏取り済のみ。

## 6. 具体の強制フロー
1. 納品型ファイルの Write/commit を hook が捕捉（未宣言はブロック）。
2. hook が独立 verifier を成果物ハッシュに対し起動 → ②URL実fetch＋含有検査／①③別AIの支持・矛盾判定 → **署名付きログ**を外部に出力。
3. hook は署名を検証。有効署名なし/未検証/型未宣言 → **ブロック（exit≠0）**。
4. 敵対的 false-negative テストを常設。

## 7. 直接検知型（#2-#5）の補修
- コマンドは string でなく**正規化/AST後**に判定（`rm -r -f`・`--force-with-lease`・`find -delete`・`shutil.rmtree` 等の回避を塞ぐ）。
- UI は拡張子でなく**出力内容**（`<html`/`<!doctype`）で判定。

## 8. 検証方法（この設計自体）
- **敵対的テストスイート必須**: 捏造定説・無関係/404 URL・自作検証ブロック・型誤申告（無害型で信頼物を出す）を hook が**全件ブロック**して初めて PASS。
- honest欠落（今回の Stage3 医療Q&Aレポート＝定説/URL/サブAI無し）も未検証としてブロックすること。
- チャット直答は「監査で検出」のみ＝**機械強制不能と明記**（過大主張しない）。

## 9. スコープと限界（正直な線引き）
- **強制可能**: ファイル成果物（納品物）。ココナラ納品は元々ファイル＝実在チョークポイントを通る。
- **強制不能**: チャット直答の信頼主張（Claude Code にアシスタント出力の hook が無い）。規律＋サブAI抜き取り監査に留め、"飛ばせない"とは名乗らない。

## 10. 未決（マスター判断）
- 型宣言 frontmatter スキーマ（必須キー・種別enum）／権威ドメイン許可リスト／署名方式。
- 独立 verifier / hook の**配備可否・場所**（vibe-base）——**担当AIは配備しない**。
