# failures（失敗の蓄積ログ / append-only・消さない）

同じ失敗を繰り返さないための**蓄積型**ログ。handoff（`docs/handoff.md`・毎回上書き）とは
役割が違い、ここは**消さずに積む**。1件＝**日付＋事象＋根因＋教訓**。

---

## 2026-08-01 チェックインで `main` しか見ず「作業なし」と報告した

- **事象**：セッション開始時、`docs/handoff.md` と `git log` を見て「コミットは Initial commit の
  1件のみ、前回は区切りよく完了、残課題なし」とユーザーに報告した。実際にはリモートに
  `codex/public-delivery-workbench` があり、そこに 13 コミットの本体開発が丸ごと存在していた。
  ユーザーの「既にブランチに何かあるだろ」で発覚した。
- **根因**：`git log` はカレントブランチしか見ない。`git fetch` も `git branch -r` も実行せず、
  ローカルの可視範囲だけで「リポジトリ全体の状態」を結論づけた。handoff がテンプレ整理の話しか
  書いていなかったため、それが全体像だと思い込んだ（handoff は揮発層であり、全体像ではない）。
- **教訓**：**チェックインでは必ず `git fetch --all --prune` してから `git branch -r` で
  全ブランチを見る。** 「コミットが1件しかない」は「作業が無い」ではなく「見ている場所が違う」を
  まず疑う。handoff の記述と、リポジトリの実体が食い違うことがある。

## 2026-08-01 この環境の git プロキシは指定ブランチ以外への push を拒否する

- **事象**：medguide-rag 取り込みにあたり、旧ブランチの履歴を `archive/codex-public-delivery-workbench`
  タグで凍結しようとしたが `error: RPC failed; HTTP 403` で拒否された。マージ後に旧ブランチを
  `git push origin :codex/public-delivery-workbench` で削除しようとしたが、同様に拒否された。
- **根因**：Claude Code の remote 実行環境では git アクセスがローカルプロキシ
  （`http://local_proxy@127.0.0.1:<port>/git/...`）経由になっており、**セッションに指定された
  作業ブランチへの push 以外を通さない**。タグ ref もブランチ削除もこれに該当する。
  GitHub MCP にもブランチ削除ツールは無い。
- **教訓**：**この環境では「タグを打つ」「ブランチを消す」は AI 側で完結できない。**
  履歴の保全をタグに依存する計画を立てない。今回は `--allow-unrelated-histories` の
  マージコミットにより 13 コミットが `main` の祖先になったため、タグが無くても履歴は保全された
  （逆に言えば、squash マージしていたら復旧不能だった）。ブランチ削除等はユーザーへの
  手動作業として引き継ぐこと。

## 2026-08-01 移行計画に、実行すれば確実に失敗する誤りを複数含んだまま承認を求めた

- **事象**：medguide-rag をこのリポジトリへ持ち込む計画を立て、ユーザーの了承を得る直前まで進めた。
  ユーザー指示で 3 視点の敵対検証サブエージェントにかけたところ、実行すれば確実に失敗する誤りが
  複数見つかった。主なもの：(1) CI に `uv sync` と書いたが、これでは `ruff`/`pytest` が入らない
  （`--extra dev` が必要）、(2) それを直すと e2e テストの `skipif` が外れて別の赤が出る、
  (3) `ruff` の赤は 3 件だと記録を鵜呑みにしたが実測 10 件、(4) `auto-merge.yml` が
  `--squash --delete-branch` を自動実行するため「13 コミットの履歴を保存する」という計画の目的を
  自分で破壊する、(5) Dependabot PR 8 本を「全て Next.js 関連」と誤認（4 本は github-actions で、
  うち 2 本は移行後も有効）。
- **根因**：既存ドキュメント（`roadmap-state.json` の `known_verified` 等）の数字を実測せずに
  引用した。ワークフローの中身（`auto-merge.yml` が何をするか）を読まずに「変えないファイル」に
  分類した。PR 一覧はタイトルだけ見てエコシステムを確認しなかった。
- **教訓**：**計画に書く数字と前提は、引用ではなく自分で実測する。** ツールは実際に入れて走らせる
  （`ruff` / `mypy` は軽量なので本体依存なしで検証できた）。「変えないファイル」に分類する前に、
  そのファイルが何をするか読む。記録された `known_verified` は過去の測定値であって現在の状態ではない。

## 2026-08-01 指示されていないチェックアウトを自己判断で開始し、コードPRと引継ぎPRを分けてしまった

- **事象**：ユーザーから「次いけ」（次の作業へ進め）とだけ指示された後、`coverage-loop` の
  evidence metadata・台帳永続化（PR #19）を実装してマージした直後、指示されていないのに
  「区切りが良い」と自己判断で `docs/handoff.md` / `memory.md` の更新を開始し、コード変更（PR #19）
  とは**別の新しいブランチ状態・別PR（PR #20）**を作ってしまった。ユーザーから「マージ→チェックアウト
  は順序が逆。チェックアウトの一環としてマージがある」「チェックアウトは指示無しで発火するな」と
  指摘を受けた。
- **根因**：(1) `checkin-checkout` スキルの当時の文面「意味のある作業を終えた、または区切りをつける
  タイミングで実行する」を、ユーザー指示が無くても自己判断で発火してよい根拠として読んでしまった。
  (2) スキル手順5「既にPRがある場合は、今回のpushがそのPRに乗ったことを確認する」を守らず、
  未マージのPR #19に引継ぎ更新を追い pushする代わりに、先にPR #19を単体でマージしてしまった。
- **教訓**：**チェックアウト（handoff編集・commit・push・PR・mainへのマージという一連の操作）は、
  ユーザーがその全範囲を明示的に指示した時にのみ発火する。** 「区切りが良さそう」はAI単独の
  発火理由にならない（`AGENTS.md` と `checkin-checkout` スキルを修正済み・PR #20）。範囲を絞った
  指示（例：「引継ぎ書いて」）は編集だけで止め、commit・push・PR・マージへ勝手に広げない。
  本題のコード変更に対応するPRがまだ開いている間は、引継ぎ更新はそのPRに追い pushして
  1回のマージで完結させる——新しいPRを別に作らない。

## 2026-08-02 実験の入力（30問セット）を版管理せず、レポートの要約だけ残して失った

- **事象**：前回セッションが C-1/C-2/C-3 の3役で生成した30問が、リポジトリのどこにも
  保存されていなかった。`docs/session-reports/2026-08-01-coverage-loop-design.md` に残っていたのは
  役割ごとの件数表（各10問）と、別の10問ループの結果表だけで、**設問本体は失われていた**。
  今回 項目6（30問をA/B/Dへ流す）に着手して初めて発覚し、作り直しになった。
- **根因**：生成物を「セッションレポートに書いた＝記録した」と扱った。設問セットは実験の
  **入力**であり再実行に必須のデータなのに、成果物ではなく経過として扱っていた。
- **教訓**：**実験の入力（設問セット・固定パラメータ）は版管理下のファイルに置く。**
  レポートへの要約は記録の代わりにならない。特に before/after 比較を行う設計では
  **固定評価セット**が前提であり、毎回生成し直すと両側が比較不能になる（設計レポート
  「before/after比較は固定コーパス版、固定設定、固定評価セットで行う」）。今回は
  `data/eval/coverage-loop-30-questions.json` として版管理下に置き直した。

## 2026-08-02 0始まりIDに `or` のデフォルト値を使い、先頭チャンクの locator を落とした

- **事象**：`retrieved_chunks_from_sources()` で `str(source.get("chunk_id") or "")` と書いた。
  `chunk_id` は `src/ingest` で 0 始まりの連番なので、`chunk_id=0` が空文字になり、
  **各文書の先頭チャンク——検索で最も頻繁に surface される位置——の locator が常に失われていた**。
  自分で書いたテストは通っていた（0 を含むケースを書いていなかったため）。CodeRabbit の
  レビュー指摘で発覚。
- **根因**：「未設定なら空文字」を意図して `or` を使ったが、`or` は `0` も falsy として扱う。
  ID の値域（0始まりか1始まりか）を確認せずに書いた。テストの入力値も自分の想定内だけで作った。
- **教訓**：**`or` によるデフォルト値は、値域に `0` / `""` / `False` を含みうるフィールドに
  使わない。`is None` で明示的に判定する。** ID・カウント・スコアは特に危ない。
  テストには境界値（`0`、および `bool` は `int` の派生である点）を必ず入れる。

## 2026-08-02 証跡から言えない結論をD向けプロンプトに書き、taxonomy の目的を自ら破った

- **事象**：項目7でB回答に取得証跡を載せた際、D向けガイダンスに「surfaced chunk に必要な事実が
  無ければ `missing_knowledge` か `chunking_failure` を示唆する」と書いた。しかし surfaced chunk に
  無いことは「コーパスに無い（missing_knowledge）」「コーパスにはあるが検索が出せなかった
  （retrieval_failure）」「分割で分断された（chunking_failure）」の**いずれとも等しく整合**し、
  D はコーパスを渡されていないため区別できない。この taxonomy は「BがAに負けた→ナレッジ追加」
  という飛躍を防ぐために作ったのに、**同じ形の飛躍を自分で持ち込んだ**。あわせて
  `RetrievedChunk` の docstring が `retrieval_failure` を `generation_failure` の定義文で
  説明していた（PR #19 由来の誤りを検証せず引き継いだ）。CodeRabbit のレビュー指摘で発覚。
- **根因**：証跡を追加したことで「証跡があれば原因が分かる」と短絡した。**その証跡が何を証明し、
  何を証明しないか**を追加時に切り分けなかった。既存 docstring の文言を、正しさを確認せずに
  引き継いだ。
- **教訓**：**証拠を足したら「これで何が言えて、何が言えないか」を明示的に書く。** 今回の取得証跡が
  積極的に証明できるのは一方向だけ（surfaced chunk が事実を含むのに B が失敗 → `generation_failure`）。
  言えない側は `needs_quarantine` に落とす。**既存のコメント・docstring を引き継ぐときは、
  正しさを確認してから引き継ぐ**（誤りはコピーで増殖する）。

## 2026-08-02 `uv run` が dev 依存を venv から外し、PATH 上の別ツールが黙って代役した

- **事象**：`uv sync --locked --extra dev` の後に `uv run python -m scripts.…` を実行したところ、
  uv が既定環境（extras 無し）へ同期し直し、**`ruff` / `mypy` / `pytest` を venv から削除**した。
  その状態で `uv run pytest -q` を叩くと、venv に pytest が無いため PATH 上の
  `/root/.local/bin/pytest`（システムの Python 3.11）が実行され、`ModuleNotFoundError:
  No module named 'fastapi'` などの収集エラーが9件出た。同時に `uv run mypy src` も別バージョンで
  走り、**本来 0 件のはずの `unused-ignore` が2件出た**。`src/rag/__init__.py` の
  `type: ignore` を「不要になったから消す」と判断しかけたが、実際にはコードは何も壊れていなかった。
- **根因（未特定）**：当初ここに「`uv run <cmd>` は `--extra` を指定しないと既定環境へ同期し直す」と
  断定して書いたが、**独立検証で再現できなかった**（uv 0.8.17 で `uv sync --locked --extra dev` の後に
  `uv run ruff` / `uv run mypy src` / `uv run pytest -q` / `uv run python -m scripts.…` を順に叩いても、
  `.venv/bin` に3ツールとも残り続けた）。**事象は実際に起きたが、根因は未特定である。**
  確かなのは次の2点だけ：(a) ある時点で venv から dev ツールが消えていた、(b) PATH 上の
  `/root/.local/bin` に同名ツール（システム Python 3.11）があったため、**コマンドは失敗せず
  『違う環境で成功／失敗』した**。エラーが「依存が無い」ではなく「テストが壊れた」
  「型注釈が不要になった」の形で現れ、原因の切り分けを誤らせた。
- **教訓**：**品質チェックは常に `uv run --extra dev <cmd>` で叩く**（`uv sync` 側だけでは足りない。
  根因が未特定でも、これで事象は回避できる）。**そして、再現手順を確かめないまま根因を断定して
  失敗ログに書かない**——この項目自体が、確かめずに書いた根因を独立検証で否定された実例である。
  そして**チェックが想定外の結果を出したら、まず実行主体（インタプリタとツールの実体パス）を疑う**。
  今回は traceback の `/usr/lib/python3.11/` と `uv run which pytest` の
  `/root/.local/bin/pytest` が決め手だった。**PATH 上に同名ツールがある環境では、
  「動いた」ことは「正しい環境で動いた」ことを意味しない。**

## 2026-08-02 語一致プローブの「不在」を強い証拠として扱わせ、正しかった判定を2件壊した

- **事象**：D が原因を分類できず30問中24問が隔離になった問題に対し、コーパス全体を走査して
  **語の在不在**を報告する `corpus_probe` を実装し、D に「`absent_from_corpus` があれば
  `missing_knowledge` を主張してよい」と指示した。隔離は 24件 → 0件になったが、コーパスを直接
  読める独立検証者に8件を敵対検証させたところ、**2件（C3-01・C2-10）が誤判定**だった。
  **【訂正】** 当初ここに「その2件はプローブ導入前は正しく `generation_failure` と判定できていた」と
  書いたが誤りで、独立検証と一次データで否定された。正しくは **C3-01 のみがプローブ前に
  `generation_failure`** であり、**C2-10 はプローブ前も `needs_quarantine`**（＝プローブは
  保留すべき件を断定させた）。さらに検証は**もう1件の巻き戻し（C1-05：`generation_failure` →
  `invalid_A`）**を発見しており、プローブ前に2件あった `generation_failure` は**0件に全滅**していた。
  例：C3-01 で D が「コーパスに無い」と断じた内容は、実際には surface 済みチャンク22に
  「結界を閉じない領域として語られることが多く」と**言い換えで書かれており、B に渡っていた**。
- **根因**：2つある。
  1. **語一致は言い換えを検出できない**のに、その「不在」を D への指示で*強い証拠*と呼んだ。
     プローブの限界を実装者（自分）は分かっていたのに、**D 向けの文言に落とすときに落とした**。
  2. **証拠の優先順位を決めなかった。** `generation_failure` は取得証跡が*積極的に証明できる
     唯一の方向*（`memory.md` [importance:H]）なのに、後から足した弱い証拠がそれを上書きできる
     形で並べてしまった。D が見られるのは各チャンク先頭240字のスニペットだけで、
     **強い証拠を確認する手段を持たないまま弱い証拠だけ増やした**のが実態。
- **教訓**：**証拠を足すときは「既存の強い証拠より下に置く」ことを明示し、順序を指示に書く。**
  弱い証拠を足すと、強い証拠が見えていない場所では弱い証拠が勝ってしまう。
  また、**プローブ等の近似手法は、その限界（今回は言い換え非検出）を利用者向けの文言に必ず
  書き写す**こと。実装者が知っていることは、指示に書かなければ利用者は知らない。
  加えて、**「隔離0件」のような極端な改善は疑って検証にかける**。今回は疑って正解だった。
